Tokenizer

A language model does not read characters or words. It reads tokens — pieces found by starting from single letters and repeatedly merging whichever adjacent pair was most common in its training text. This one was trained on the twelve pieces on this site, which is why it knows Bangladesh as one token and has to spell out anything it has never met.

{%- comment -%} Bangladesh sits mid-sentence on purpose. At the start of the string it has no leading space, so it is a different pre-token — "Bangladesh" rather than "▁Bangladesh" — and encodes as three pieces instead of one. That is correct behaviour and worth meeting, but not while the paragraph above is claiming the corpus knows the word. {%- endcomment -%} {%- comment -%} Samples chosen to show both directions. The first is dense in corpus vocabulary and encodes tightly; the second is technical English this site has never used and shatters into letters. Watching the chars-per-token figure move between them is the whole lesson. {%- endcomment -%}

Why this matters

Tokens are the unit everything is priced and limited in. A context window is counted in them, an API bill is counted in them, and the ratio of characters to tokens is not a constant — it depends entirely on how well the text matches what the tokenizer was trained on. English prose runs around four characters per token. Code, unusual names, and languages written in a script the training data barely contained run far worse, which is a real and underappreciated cost asymmetry.

This one has {{ bpe.vocab }} tokens against GPT-2's 50,257, and no byte fallback — a character the corpus never contained simply has no id here, where a production tokenizer would drop to raw bytes so that nothing is unencodable. Otherwise it is the same algorithm, in about twenty lines of assets/js/tokenizer.js. Everything modern tokenizers add is engineering around edge cases rather than a different idea.
