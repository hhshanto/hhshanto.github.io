WHY THE HIERARCHY IS THE SKELETON. The obvious design is posts joined by shared tags, and that is what this started as. It does not work here: at the time of writing, eleven of thirteen pieces carry no `tags:` at all, so a tag graph is a field of unconnected dots. What the site does have, and has had since long before the redesign, is a two-level filing structure — five domains, each with sub-topic directories — which _layouts/category.html already reads off `doc.path`. That is the skeleton here, derived the same way and for the same reason. Tags are then drawn on top as cross-links, and that is the point of the screen rather than a consolation: a piece with no tags hangs off its own branch and nothing else, and the map shows that at a glance. Tag a post and it grows an edge to everything it belongs with. The map is a picture of how connected the writing actually is, so it is worth something even while the answer is "barely". NO DATA BLOB. Every node carries its own facts in data-* attributes and JS reads them back off the DOM, the way _includes/post-row.html feeds archive-filter.js. A parallel JSON copy of the same values would be a second thing to keep in step. The one derivation left to JS is which pairs of posts share a tag — Liquid can compute it, but only as an O(n²) nested loop emitting a blob, and the same loop is four lines of JS over data-tags. WITHOUT SCRIPTING the list below is a plain indented outline of the site: domain, sub-topic, pieces. The map is layered on by adding `is-live`, so nothing here depends on JS to be readable. {%- endcomment -%} {%- assign pool = '' | split: '' -%} {%- for domain in site.data.domains -%} {%- assign pool = pool | concat: site[domain.collection] -%} {%- endfor -%} {%- assign all_docs = pool -%} {%- comment -%} Tagged-piece count, for the readout's resting state.
